# Push Notifications — Backend (Laravel)

> Companion doc for frontend: `PUSH_NOTIFICATIONS_FRONTEND.md`

---

## 1. Important rule for our app

Login is **optional** in our app. So we send push notifications to the **device**, not the user.

- Every install gets a `device_id` (UUID generated by the Flutter app, sent to us).
- We store FCM tokens against `device_id`, not `user_id`.
- `user_id` column is **nullable** — set when user logs in, cleared when they log out.
- Device row is **never deleted on logout** — anonymous users keep getting location-based pushes.

### Step 2 — Create `device_tokens` table

```sql
CREATE TABLE device_tokens (
    id            BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
    device_id     VARCHAR(64)  NOT NULL UNIQUE,    -- UUID from Flutter
    user_id       BIGINT UNSIGNED NULL,            -- NULL when not logged in
    fcm_token     VARCHAR(255) NOT NULL,
    platform      ENUM('android','ios') NOT NULL,
    app_version   VARCHAR(50)  NULL,
    state_ids     JSON NULL,
    district_ids  JSON NULL,
    mandal_ids    JSON NULL,
    last_seen_at  TIMESTAMP    NULL,
    created_at    TIMESTAMP    NULL,
    updated_at    TIMESTAMP    NULL,
    KEY idx_user (user_id),
    KEY idx_device (device_id),
    FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE SET NULL
);
```

After backfilling existing tokens → drop `users.fcm_token` column.

### Step 3 — Build new endpoints

| Method | Path | Auth | Purpose |
|--------|------|------|---------|
| `POST` | `/api/device-tokens` | None | Upsert by `device_id`. If auth header present, also set `user_id`. |
| `POST` | `/api/device-tokens/link` | Required | Set `user_id` on the row matching `device_id`. (After login.) |
| `POST` | `/api/device-tokens/unlink` | None | Clear `user_id` on the matching row. **Keep the row.** (On logout.) |
| `GET` | `/api/notifications` | Required | Paginated inbox — see §5. |
| `GET` | `/api/notifications/unread-count` | Required | `{ "unread_count": 3 }` |
| `POST` | `/api/notifications/{id}/mark-as-read` | Required | Already exists — keep. |
| `POST` | `/api/notifications/mark-all-as-read` | Required | Already exists — keep. |
| `DELETE` | `/api/notifications/{id}` | Required | Delete one. |
| `POST` | `/api/admin/notifications/broadcast` | Admin | Replaces current `sendNotification`. **Must be queued.** |

**Remove** `POST /api/fcm-token` (replaced by `/api/device-tokens`).

### Step 4 — Role-based notification flow (IMPORTANT)

Our app has these role slugs (already in DB): `admin`, `subadmin`, `dist-reporter`, `reporter`, `reader`.

A single news upload triggers **multiple notification waves at different stages**:

```
STAGE 1 — Reporter uploads news (status = pending)
         ↓
         Notify editors who cover that location
         (subadmin / dist-reporter in the news's state + district)
         Type: news_pending_review
         Deeplink: deeppulse://admin/review/{news_id}

STAGE 2 — Editor / admin approves news (status = published)
         ↓ (3 parallel pushes)
         ├─► Notify the reporter (their news was approved)
         │   Type: news_approved
         │   Deeplink: deeppulse://news/{news_id}
         │
         ├─► Notify all admins (visibility)
         │   Type: news_admin_notice
         │   Deeplink: deeppulse://admin/news/{news_id}
         │
         └─► Notify all devices in news's location
             (anonymous + logged-in readers)
             Type: news_published
             Deeplink: deeppulse://news/{news_id}
```

If an `admin` / `subadmin` uploads directly (auto-published), Stage 1 is skipped — Stage 2 fires immediately.

### Full trigger table

| Trigger | When it fires | Audience query | Type |
|---------|--------------|----------------|------|
| News pending review | Reporter creates news with `status=pending` | Logged-in users with role IN (`subadmin`,`dist-reporter`) AND `state_id` = news state AND `district_id` = news district | `news_pending_review` |
| News approved | News status flips `pending → published` | Reporter's own devices | `news_approved` |
| News rejected | Editor rejects news | Reporter's own devices | `news_rejected` |
| News published (admin notice) | Status becomes `published` | All devices of users with role = `admin` | `news_admin_notice` |
| News published (readers) | Status becomes `published` | All devices (anonymous + logged-in) whose `state_ids` / `district_ids` / `mandal_ids` overlap the news's locations | `news_published` |
| Comment on user's news | New comment on a news a user uploaded | News uploader's devices | `comment_on_news` |
| Reply to user's comment | Reply to user's comment | Comment author's devices | `comment_reply` |
| Admin announcement | Manual admin broadcast | Filtered devices | `admin_announcement` |

Implement each as a Laravel Notification class with `database` + `fcm` channels.

### Step 5 — Targeting queries

**A. News pending review (Stage 1 — to editors of that location):**
```sql
SELECT dt.fcm_token
FROM device_tokens dt
JOIN users u   ON u.id = dt.user_id            -- only logged-in users
JOIN role_user ru ON ru.user_id = u.id
JOIN roles r   ON r.id = ru.role_id
WHERE r.slug IN ('subadmin', 'dist-reporter')
  AND u.state_id    = <news.state_id>
  AND u.district_id = <news.district_id>;
```

**B. News published — readers in news's location (Stage 2):**
```sql
SELECT fcm_token
FROM device_tokens
WHERE JSON_OVERLAPS(state_ids,    JSON_ARRAY(<news.state_ids>))
   OR JSON_OVERLAPS(district_ids, JSON_ARRAY(<news.district_ids>))
   OR JSON_OVERLAPS(mandal_ids,   JSON_ARRAY(<news.mandal_ids>));
```

**C. News published — admin notice (Stage 2):**
```sql
SELECT dt.fcm_token
FROM device_tokens dt
JOIN users u   ON u.id = dt.user_id
JOIN role_user ru ON ru.user_id = u.id
JOIN roles r   ON r.id = ru.role_id
WHERE r.slug = 'admin';
```

**D. News approved / rejected — uploader (Stage 2):**
```sql
SELECT fcm_token
FROM device_tokens
WHERE user_id = <news.uploader_id>;
```

- Chunk every result set into batches of **500** (FCM multicast limit).
- Send inside a **queued job** — never synchronously inside the request.

### Step 6 — Token hygiene
After every FCM send, check the response:
- `UNREGISTERED` or `INVALID_ARGUMENT` → **delete that `device_tokens` row**.
- Other errors → log but keep.
- Logout = unlink (clear `user_id`), NOT delete.

### Step 7 — Security
- Add admin role middleware to `/api/admin/*` routes.
- Validate that `state_ids[]`, `district_ids[]`, `mandal_ids[]` reference real rows.
- Rate-limit `/api/device-tokens` to prevent abuse.

## 5. What we send to FCM (must follow this contract)

`notification` block (rendered by the OS):
```json
{
  "title": "Breaking news in your district",
  "body":  "Short summary",
  "image": "https://cdn.deeppulse/news/1234/thumb.jpg"
}
```

`data` block (drives in-app routing — **all values must be strings**):
```json
{
  "type":         "news_published",
  "entity_id":    "1234",
  "entity_type":  "news",
  "deeplink":     "deeppulse://news/1234",
  "image_url":    "https://cdn.deeppulse/news/1234/thumb.jpg",
  "click_action": "FLUTTER_NOTIFICATION_CLICK"
}
```

For Android, also set `android_channel_id: "deep_pulse_default"`.

`type` values: `news_published`, `news_approved`, `news_rejected`, `comment_on_news`, `comment_reply`, `admin_announcement`, `test`.
